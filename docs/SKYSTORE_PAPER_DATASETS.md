# SkyStore 论文（`skystore.pdf`）中的数据集与工作负载说明

本文根据 VLDB 论文 *SkyStore: Cost-Optimized Object Storage Across Regions and Clouds*（仓库根目录 `skystore.pdf`，arXiv:2502.20818）**第 6.1 节**及 **Figure 4 / Table 2** 整理，便于对照 **artifact 中的 SNIA 构造脚本**与 **`Data/`** 中的 trace 文件。

---

## 1. 数据来源与共性

| 维度 | 论文描述 |
|------|-----------|
| **原始轨迹** | **SNIA IBM Object Store traces**（引用 SNIA IOTTA，论文参考文献 [10]），记录 **一周** 内对 **单个 bucket** 的 RESTful 操作（GET、PUT、HEAD、DELETE 等）。 |
| **地理含义** | 轨迹来自 **IBM Cloud 内单一区域** 的请求序列；**并非**天然的多云、多区域 trace。 |
| **选取方式** | 从大量 trace 中选出 **5 条代表性轨迹**（文中记为 **T15、T29、T65、T78、T79**），在 **新近性、频率、对象大小、突发性、PUT/GET 分布** 等维度上具有 **鲜明且互不相同的特征**。 |
| **时间尺度扩展（仿真用）** | 对象存储中数据常保留 **数月到数年**，而原始 trace 仅一周。论文将 trace 中 **「1 个日历日」拉伸为「1 个月」（单云实验）或「3 个月」（多云实验）**，**不改变** 固有的 **读写比例** 与 **请求分布形状**。 |
| **与多区域/多云实验的关系** | 公开数据中 **没有** 真实多云 trace；作者在原始单区域 trace 上 **合成** 多区域、多云工作负载（见第 3 节）。 |

**共性小结**：五条 trace **同源、同结构（单桶一周 REST）**；差异主要体现在 **对象大小分布、读重复度、时间突发性、访问新近性、读写比例** 等维度，用于覆盖 **策略在不同代价敏感方向** 上的表现。

## 2. 五条 IBM 轨迹的个性（§6.1.2 + Figure 4）

论文从五个维度刻画差异：**对象大小**、**访问频率（含 one-hit）**、**突发性**、**新近性**、**GET/PUT 比例**。下列为文中对 **各 trace 的对比性结论**（具体百分比以原文 Figure 4 与 Table 2 为准）。

### 2.1 对象大小（四类：Tiny &lt;1KB，Small 1KB–1MB，Medium 1MB–1GB，Large &gt;1GB）

- **多数 trace**：访问对象以 **small / medium** 为主；**large** 极少。
- **Tiny 对象比例**：多数 trace **&lt;0.5%**，**例外为 T29 与 T65（约 30%–45% tiny）**。
- **Small**：所有 trace **&gt;35%**；**T15、T29、T78** 中 **small 占多数（约 56%–97%）**。
- **Medium**：**T65** 约 **34%**、**T79** **&gt;60%** 为 medium；**其余 trace** 中 medium **&lt;20%**。
- **Large**：仅 **T65、T79** 出现，且 **极少（&lt;0.4%）**；**其余 trace 无 large**。

### 2.2 访问频率与「单次命中」（One-hit / Cold / Warm / Hot / Super-hot）

论文将对象按 GET 次数分为：one-hit（1 次 GET）、cold（1–10）、warm（10–100）、hot（100–1000）、super-hot（&gt;1000）。

- **T15、T29**：**几乎由 one-hit 与 cold 主导**（重复读很少；Figure 4b 与文中描述强调与 T65/T78 的差异）。
- **T78**：**warm 对象占多数（&gt;51%）**。
- **T65**：**hot 对象占多数（&gt;67%）**。
- **Super-hot**：仅 **T65、T78** 有 **极少量（&lt;0.1%）**。

### 2.3 突发性（Burstiness）

定义为 **随时间分布的 GET 比例**（Figure 4c）。

- **T15**：时间上 **相对均匀**；且 **最后两个月几乎无访问**。
- **T78**：**最后两个月内集中约 60% 的 GET**（强尾部突发）。
- **其余 trace**：约 **50%** 访问落在 **最后两个月**。
- **T29、T65、T79**：GET 在时间轴上 **相对更均匀**，但仍有 **短间隔尖峰**（约 **30%** 对象在 **短间隔** 内被访问）。

### 2.4 新近性（Recency，连续 GET 间隔）

- **T15、T78**：大量间隔在 **一天以内**。
- **T65、T79**：约 **10%** 的 GET 间隔落在 **一天到一个月** 之间。
- **T29**：**&gt;80%** 的读取间隔在 **一天到约两个月**；**更长间隔** 也占相当比例。

### 2.5 GET 与 PUT 比例

- **读多（read-heavy）**：**T65、T78、T79**。
- **写多（write-heavy）**：**T15、T29**（文中给出约 **42%** 与 **30%** 为 PUT）。
- **T29**：总请求量 **超过 1200 万**，属 **极高请求数** trace，对 **按请求计费** 敏感。

### 2.6 Table 2（论文）中的汇总字段

论文 **Table 2** 为每条 trace 汇总了：**各尺寸桶占比、平均大小、one-hit/cold/warm/hot/super-hot、请求到达时间分布、GET 尾部（tail）与 PUT/GET 比例、总请求数（百万级）** 等。若需与仿真器 `All_Results.csv` 对照，应以 **同一 Part 编号 + 同一合成方式（typeA 等）** 为准。

## 3. 从单区域 trace 到「多区域 / 多云」工作负载（§6.1.3）

论文用 **三步** 将 **单区域 IBM trace** 转为实验用工作负载：

1. **单云两区域（base + cache）**：PUT 落在 **base**，GET 落在 **cache**，对应常见「数据在一区、计算在另一区」场景。
2. **多区域与多云**：在 industry 观察基础上定义四类合成模式（**Type A–D**）：
   - **Type A（Uniform）**：PUT/GET 在区域间 **均匀随机**（如 IoT、电商类随机访问）。
   - **Type B（Region-aware）**：每个对象有 **固定 PUT 区与 GET 区**（卫星图、灾备、云突发等）。
   - **Type C（Aggregation）**：多区 **写入**，**集中一区读取**（日志/销售汇总等）。
   - **Type D（Replication）**：**单区写入**，多区读（CDN、镜像仓库、分布式推理等）。
3. **Type E（Multi-cloud 组合）**：将多类工作负载 **组合**；论文说明仅在 **T65** 上做 **端到端真实云部署**（成本原因：每条 trace 平均约 **6.7 TB** 数据，全组合实验可达约 **20 万美元量级**）。

**与仓库 artifact 的对应**：`SNIA_traces/yaml/` 中的 **typeA / typeB / …** 及 `new_trace_gen.py` 即实现上述 **合成多区域访问**；**本仓库 `Data/`** 常见命名为 **`IBMObjectStoreTrace0xxPart0.typeA.mc.aug`**，表示在 **IBM Part0** 上施加 **Type A** 映射后的结果。

## 4. 共性 vs 个性（设计实验时的用法）

| | **共性** | **个性（选 trace 时利用）** |
|---|-----------|-----------------------------|
| **来源与格式** | 均为 SNIA IBM、单桶、一周 REST；经论文规则 **时间拉伸** 与 **区域合成** 后用于仿真。 | **T29**：极小对象 + 超高请求数 → **API/请求费** 压力；**T65/T79**：大中对象 + 读多/热对象 → **存储与带宽** 压力；**T15**：偏写、偏 one-hit/cold → **少副本/激进驱逐** 基线；**T78**：warm、突发在尾部 → **TTL/直方图** 与 **长尾读**；**T65**：hot、混合尺寸 → **缓存命中与复制** 收益。 |
| **策略对比** | 同一 **placement/eviction** 应在多条 trace 上评估，避免过拟合。 | 论文强调 **SkyStore 相对 CGP（全知）** 在 **T78、T79** 等 **混合分布** 上差距略大（**bucket 级统计** 粒度限制），与 **per-object** 方法对比时可引用该讨论。 |
