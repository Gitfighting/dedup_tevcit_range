## 摘要（Abstract）

随着云存储的普及，数据去重已成为广泛使用的技术：通过消除跨用户的重复数据来节省网络带宽。然而，传统数据去重难以在**相似块（resemblance chunks）**之间检测重复数据。目前已有名为 **Finesse** 的相似数据去重方案，能够高效检测并删除相似块中的重复数据。

然而，我们观察到：**紧跟在相似块之后的块，很可能同样具有数据局部性（data locality）**；反之亦然。若对这些相邻相似块一律按**较小的平均块大小**处理，会显著增加**元数据（metadata）**，从而损害去重系统性能。此外，现有相似数据去重方案**忽视了元数据对性能的影响**。

因此，我们提出一种**面向云存储的快速可变粒度相似数据去重**方法：动态合并相邻的相似块或唯一块，或在**相似块与唯一块之间的过渡区域**对块进行拆分。最后，我们实现原型并在真实数据集上进行一系列实验。结果表明，该方法在保持高去重率的同时，**大幅降低了元数据规模**。

**索引词（Index Terms）**：相似数据去重（Resemblance Data Deduplication）、云存储（Cloud Storage）、元数据规模（Metadata Size）、可变粒度（Variable-Grained）

## I. 引言（INTRODUCTION）

随着互联网与电子设备的发展，人们越来越倾向于将数据外包到云存储，例如 Google Drive、Dropbox 和百度网盘 [1]。这为外包数据提供了更高的灵活性与可靠性。毫无疑问，在多用户云存储场景中存在大量冗余；这些重复数据显著降低存储利用率，并浪费部分网络带宽。因此，许多研究者在存储处理过程中引入**数据去重**技术以消除冗余。

数据去重基于数据的哈希值（如 **Rabin 指纹**值）检测重复：相同数据共享同一哈希值，去重系统根据检测结果不再存储重复数据。为在这些数据中挖掘更多冗余，研究者将大数据切分为小块。例如，分块算法已从**定长分块**演进到**内容定义分块（content-defined chunking）**，如 BSW [2]、TTTD [3]、Elastic Chunking [4] 和 Fast CDC [5]。因此，块越小，通常能发现的冗余越多。

然而，传统数据去重工作只能检测**完全重复**的数据，无法消除**相似数据（resemblance data）**中的冗余。具体而言，两个块若大部分内容相同、仅少数字节不同，则哈希值不同；传统去重因哈希不同而将其视为唯一块。显然，相似块之间的冗余难以被检测。此外，多用户存储场景中存在大量此类冗余；若能检测并删除相似块中的重复部分，可进一步节省网络带宽与云存储空间。

作为代表最新进展的工作，**N-transform [6]** 与 **Finesse [7]** 被提出：先检测冗余数据，再使用 **delta 压缩**删除冗余部分，仅存储唯一内容。为保证较高的相似检测效率，N-transform 为每个块生成特征；两个块是否相似取决于**特征距离**——距离越短，越相似。N-transform 提取块内所有 Rabin 指纹 [8]，将所有 Rabin 指纹值线性变换 N 次，得到 N 维哈希集合，再从每一维中选取最大值作为特征。尽管如此，N-transform 因线性变换过程而承受较高的特征计算开销。

为进一步加速相似检测，Finesse 采用**分组策略**计算块特征 [7]：将块划分为子块，提取对应 Rabin 指纹并放入若干等长的连续集合，再基于各集合内值的**秩（rank）**分组构成特征。Finesse 的目标是在相似检测上优于 N-transform。尽管 Finesse 通过省去变换过程提升了相对 N-transform 的性能，现有相似检测方案（包括 Finesse）**忽视了元数据这一对去重性能至关重要的因素**。

因此，根据先前研究 [9]，**元数据因素**对去重系统性能至关重要：平均块越小，产生的元数据越多。小块虽能检测更多重复数据，也会带来大量元数据，显著增加数据管理难度（如**数据碎片化**问题）。因此，去重比（deduplication ratio）也应考虑元数据因素，其定义为：

**去重比 = 未处理前的整体存储大小 /（处理后的存储大小 + 元数据大小）**

在相似数据去重中，情况会更糟：最新相似检测工作引入大量计算，并产生更多元数据，包括**块特征、校验码和块序列信息**等。

总之，数据去重是云存储场景中的关键技术；删除相似数据中的重复部分可大幅节省带宽并提高存储利用率。然而，现有相似数据去重方案未在去重过程中考虑元数据因素。因此，我们在相似检测中考虑元数据因素，提出**面向云存储的快速可变粒度相似数据去重**。

**本文核心思想**：通过**可变粒度**的相似块检测，避免不必要的相似检测计算并降低元数据规模——对**高冗余概率**的数据以**细粒度**切分，对**低冗余概率**的数据以**粗粒度**处理。

**主要贡献如下**：

- **第一**，我们分析现有相似数据去重方案的局限。元数据规模对去重性能至关重要；在相似去重中**动态合并相邻相似块或唯一块**，可能显著降低元数据规模。

- **第二**，基于上述观察，我们提出快速可变粒度相似数据去重方案，通过可变粒度相似块检测避免不必要的相似检测计算并降低元数据规模。

- **第三**，我们进行大量仿真实验评估设计。实验结果表明，本文方法在元数据规模与去重比上优于最新工作。

**论文结构**：第二节总结相似数据去重相关工作；第三节分析最新相似检测工作在去重中的问题；第四节提出面向云存储的快速可变粒度相似数据去重；第五节给出实验结果；第六节总结全文。

## II. 相关工作（RELATED WORK）

随着云存储技术普及，数据去重成为实现高存储利用率、节省网络带宽的关键技术，其收益吸引了大量研究者。本节按是否支持**相似检测**，将相关工作分为两类。

### A. 传统去重（Traditional Deduplication）

传统去重的主要思想是比较每个块的哈希值以删除重复数据 [10]，仅存储唯一块。该思想已用于多种云存储场景，如主存储与备份级存储 [11]–[14]。其他系统采用不同方法提升去重效果，例如将块级去重与压缩结合 [15]、全局去重 [16] 等。此外，数据去重在虚拟机镜像 [17]–[19] 上也受到广泛关注。

然而，根据我们的观察，在**非重复但高度相似**的块之间存在大量冗余；现有传统去重难以检测并删除相似块之间的重复部分。

### B. 相似数据去重（Resemblance Data Deduplication）

为检测并删除相似块中的重复部分，一些研究者采用 **delta 压缩**这一数据缩减技术以最大化压缩比 [6], [20]。delta 算法以 delta 格式记录相似块之间的差异，仅将差异写入 delta 文件。然而，delta 压缩本身无法回答**哪些块应作为 delta 压缩的候选**。因此，**相似检测**是 delta 压缩的第一步，用于确定各块之间的相似关系。

Aronovich 等人 [21] 提出一种用于去重系统的新型相似签名，将相似匹配方案与逐字节比较或基于哈希的身份方案结合。Xu 等人 [22] 针对数据库管理系统提出基于相似度的去重系统，通过字节级编码获得更大节省。还有一些**粗粒度**相似检测方法 [6], [23], [24]：从非重叠块中提取特征，但可能产生较高误报率。

作为较新的工作，**N-transform [6]** 与 **Finesse [7]** 尝试通过**分组特征机制**提升相似检测精度与性能。二者均为**块级**相似检测。N-transform 提取块内 top-k 最大 Rabin 指纹值，再由若干此类特征计算块的 super-feature。Finesse 则在每个子块中提取最大 Rabin 指纹值，并按这些值的**排序**分组构成特征。

然而，根据先前研究 [9]，**元数据因素**对去重系统性能至关重要：平均块越小，元数据越多。在考虑相似检测时，情况会更糟——最新相似检测工作引入大量计算并产生更多元数据，包括块特征、校验码和块序列信息。**现有相似检测方法在去重处理过程中未考虑元数据**。

## III. 问题陈述（PROBLEM STATEMENT）

本节主要讨论现有相似数据去重的局限。为删除相似块之间的冗余，多数研究者通过提取各块内容特征来衡量块间相似度。最常见的特征提取方法是：选取块内 **top-k 最大 Rabin 指纹值**作为特征，再基于这些特征测量相似距离，并仅存储与最相似块对之间的差异部分。

然而，现有相似数据去重方案 [6], [7] **未考虑元数据因素**，可能损害性能并增加管理复杂度。

**传统去重系统中的元数据**描述块的基本哈希值，以及块与原始数据之间的关系。相似数据去重中的元数据规模比传统去重更大：除传统元数据元素外，还包括每个块的特征（一组哈希值），所有特征都需记录在元数据中。随着特征维度上升，元数据规模会急剧增大。

元数据膨胀会严重损害去重系统中**上传与下载**过程的性能。具体而言，元数据规模与去重中的**块数量**相关。为发现更多重复数据，往往采用**细粒度平均块大小**；其负面影响是元数据增大并损害上传性能——即便存在块容器（chunk container）方案，过多小块的上传仍会降低系统性能。类似地，去重中的**恢复过程**也需基于元数据组装这些块；在相似数据检测中，情况会更糟。此外，现有相似数据去重方案几乎不考虑元数据因素。

**进一步观察（本文设计动机）**：

1. 基于**数据局部性**，紧跟在相似块之后的块也很可能相似，反之亦然。

2. 若将两个相似块的 delta 编码结果视为一种压缩结果，则**分别**对相邻相似块做 delta 编码的压缩结果，往往**大于**将这些块**作为整体**处理时的压缩结果。

3. 不加区分地对所有这些块一律采用细粒度处理，也会增加元数据规模。

因此，我们假设：在相似数据去重中**动态合并相邻相似块或唯一块**，可能显著降低元数据规模；同时，对位于**相似块与唯一块之间过渡区域**的块进行**拆分**，有助于删除更多重复数据。受这些观察启发，我们尝试设计**快速可变粒度相似数据去重**方案。

## IV. 系统设计（SYSTEM DESIGN）

本节首先介绍相似数据去重设计的**高层工作流程**；接着详述**快速可变粒度相似检测方案**，目标是在保持高去重比的同时降低元数据规模；最后简要描述实现。

### A. 工作流程概览（the Overview of Workflow）

基于上述观察，我们的设计必须：通过可变粒度相似块检测，**避免不必要的相似检测计算**并**降低元数据规模**。因此，我们先以**粗粒度**处理**低重复概率**的数据片，再对**高冗余概率**的数据片以**细粒度**进一步切分。为便于描述，我们将设计分为**上传**与**下载**两个过程，如图 1 所示。

#### 上传过程（Uploading）

1. 目标上传数据按**粗粒度平均块大小**切分为块（CDC，滚动窗口）。

2. 通过与服务器交互，将这些块分为三类：**过渡区域块（Transition region chunk, T）**、**重复块（Duplicate chunk, D）**、**非重复块（Non-duplicate chunk, N）**。由于这些块处于粗粒度层级，客户端较易获得分类信息。

3. 客户端根据 **重复块数 / 总块数** 计算目标数据的**重复块比例** \(R\%\)。

4. 客户端决定是否将整块或部分块进一步细分为子块：
   - **4.1** 若 **重复块比例 ≥ 阈值**：对属于过渡区域 \(T_i\) 的块进行**细粒度**切分，并将不同粒度级别的块放入不同集合。
   - **4.2** 若 **重复块比例 < 阈值**：对标记为 \(D_i\) 或 \(T_i\) 的**非重复块与过渡区域块**进行细粒度切分。

5. **相似块处理**：对非重复块或子块提取特征（feature 1, feature 2, feature 3…），通过与服务器的**特征库（Features Repository）**交互进行**相似检测（Resemblance Detection）**。若 chunk i 与 chunk b 相似，则 chunk i = chunk b + delta' 文件。客户端向服务器发送 delta、元数据文件与不相似块。

**图 1 上传侧符号说明**：
- **T**：过渡区域块  
- **D**：重复块  
- **N**：非重复块  
- **T Set**：过渡/细分子块集合  
- **BSet**：粗粒度唯一块集合  

#### 下载过程（Downloading）

1. 客户端发起**远程文件请求**（Request file i）。

2. 服务器在**元数据仓库（Metadata Repository）**中查找对应元数据（metadata i），其中记录例如：
   - 0–920B → chunk g  
   - 920–1689B → chunk h  
   - 1689–2425B → delta i  
   - …  
   - …–1MB → chunk j  

3. 根据元数据在**文件仓库（File Repository）**中定位相应块、子块与 delta 文件。

4. **文件恢复（File recovery）**：对 delta 文件解码（Decode delta files），执行 delta 编码的逆操作，按元数据中的恢复顺序拼接 chunk g、chunk h、sub-chunk i … sub-chunk i+2 等，组成 File i 并发送给客户端。

需要指出，**可变粒度相似块检测**大幅避免不必要的相似计算，并显著降低元数据规模（详见下一小节）。

### B. 快速可变粒度相似检测方案（Fast Variable-Grained Resemblance Detection Scheme）

本小节详述快速可变粒度相似检测方案，如**算法 1** 所示。

为在相似数据检测中**动态**检测重复数据，我们引入两种平均块大小：
- **粗粒度平均块大小**（coarse-level average chunk size）
- **细粒度平均块大小**（fine-grained average chunk size）

对每个目标数据 \(fp\)，方案首先按粗粒度平均块大小 `avg_chunk_size` 将 \(fp\) 切分为块。客户端可判断每个块是否唯一：若云服务器未存储该块的哈希值，则视为唯一块。客户端再根据这些块的顺序标记重复块位置。

随后，客户端得到一系列顺序排列的粗粒度块。为便于后续细粒度处理：
- 每个**与重复块相邻**的唯一块，按细粒度平均块大小 `grain_size` 切分为子块，子块集合定义为 **T Set**；
- **不与重复块相邻**的唯一块，直接放入 **B Set**。

客户端计算每个粗粒度块的哈希值并标记重复块位置。粗粒度分块完成后，客户端统计目标数据中重复块占比 **init_dup_ratio**。

统计 init_dup_ratio 的主要目的是**加速相似块检测**：若 init_dup_ratio **小于阈值**（预定义值），客户端将对 BSet 中**全部**唯一块以细粒度进一步处理——将 BSet 中每个元素按 `grain_size` 切分为子块并移入 TSet，并清空 BSet。

最后，对 TSet 与 BSet 中每个元素，基于 **Finesse [7]** 计算块特征。服务器收到块或子块特征后，可选出相似块，并通过 **delta 编码**记录差异部分。

**相似去重中的元数据**包括：唯一块或子块的特征、块哈希值、块/子块与目标数据之间的关系信息等。

#### 算法 1：快速可变粒度相似检测方案（完整中文对照）

```
算法 1  快速可变粒度相似检测方案
输入：
  fp            — 目标数据路径
  avg_chunk_size — 粗粒度平均块大小
  grain_size     — 细粒度平均块大小
输出：
  Delta 文件, 元数据

1:  按 avg_chunk_size 将目标数据 fp 切分为粗粒度块 ck1, ck2, …, cki
2:  for ck1 in cki do
3:      计算每个 cki 的哈希值，并标记重复块位置 → 集合 L
4:  end for
5:  for L 中每个元素 do
6:      if 第 i 个元素是唯一块 且 与重复块相邻 then
7:          按 grain_size 将 cki 切分为子块 sub_ck1, sub_ck2, …, sub_ckj
8:          块集合 TSet ← sub_ckj
9:      else if 第 i 个元素是唯一块 且 不与重复块相邻 then
10:         块集合 BSet ← cki
11:     end if
12: end for
13: init_dup_ratio ← 重复块数量 / 总块数量
14: if init_dup_ratio < threshold then
15:     TSet ← 将 BSet 中每个元素按 grain_size 切分后并入 TSet
16:     清空 BSet 中所有元素
17: end if
18: for TSet 与 BSet 中每个元素 do
19:     计算该元素特征；基于服务器特征历史记录，通过向量距离选出相似块
20:     执行 delta 编码，并记录 delta 与元数据
21: end for
```

### C. 实现（Implementation）

我们采用传统**内容定义分块（CDC）**算法作为切分算法。每种 CDC 算法都有平均块大小参数；本设计使用两类参数：
- 粗粒度平均块大小 `avg_chunk_size`
- 细粒度平均块大小 `grain_size`

算法 1 中的**阈值**设为 **0.01**（经验值），将在未来工作中进一步研究。

**块特征提取**与 Finesse [7] 相同：提取块内 top-k 最大 Rabin 指纹值，由若干此类特征计算 super-feature；客户端在每个子块中提取最大 Rabin 指纹值，并按值的排序分组构成特征。

**Delta 编码**实现采用 **VCDiff [25]**。

## V. 实验评估（EVALUATION）

### A. 数据集（DataSets）

为评估方法有效性，我们选取三个不同的真实工作负载：

1. **macOS 工作负载 [26]**：收集同一天多位用户的快照，代表**去重率较低**的工作负载。

2. **Kernel 数据集 [27]**：来自 Linux 内核归档网站。

3. **SQL Dump 数据集**：包含不同时期的备份，由 [28] 报告。

这些工作负载包含用户日常使用的多种修改模式。我们在这些数据集上进行实验，以公平评估设计收益。

### B. 评价指标（Metrics）

使用两个指标评估效率：

1. **Delta 压缩比（DCR, Delta Compression Ratio）**  
   \[
   \text{DCR} = \frac{\text{未处理前的整体存储大小}}{\text{处理后的存储大小} + \text{元数据大小}}
   \]  
   采用 DCR 以**考虑元数据因素**的方式评估收益。

2. **总耗时（overall time）**：CPU 执行时间。相似去重中速度性能同样关键，因此引入总耗时指标。

**实验平台**：模拟云的三台机器组成的集群。每台：Intel Core i7-4790 @ 3.60GHz、8 核 CPU、16GB RAM、500GB 5400rpm 硬盘、100Mbps 网络；操作系统 Ubuntu 18.10 LTS 64-bit。

### C. 数值结果与讨论（Numerical Results and Discussions）

#### macOS 工作负载 — DCR（图 2）

如图 2 所示，当平均块大小为 **2KB、4KB、16KB** 时，本文方法的 DCR 分别比 Finesse **高 3.71%、4.68%、1.64%**。

本文设计利用**相似数据的局部性原则**（即相似数据周围更可能出现相似数据）：按粒度划分数据，聚焦最可能包含相似数据的部分；在保证去重效率的同时，减少因块数增加导致的**元数据开销**。

Finesse 采用分组策略，在不考虑元数据的情况下按内容切分块，再提取块特征向量、判断相似数据并执行去重。由于子块数量过多，元数据规模也增大；相比之下 Finesse 的 DCR 较低，且在文件恢复时元数据检测增加，不利于恢复。

同时可见：当块长度从 4K 增至 8K，本文与 Finesse 的 DCR 差距逐渐缩小；当块长度为 **16K** 时，Finesse 的 DCR 与本文方法几乎相同——块长度增大时，文件可能被当作单块处理，块的局部性原则难以发挥作用；而 Finesse 中所有块均为细粒度。此外，块长度增大时元数据开销逐渐减小。总体而言，随着块长度增加，Finesse 与本文方法的 DCR 差距逐渐缩小。

**图 2**：macOS 工作负载上的 DCR（Average Chunk Size: 2KB / 4KB / 8KB / 16KB）

---

#### Linux Kernel 工作负载 — DCR（图 3）

Kernel 数据集中相似数据较少，难以按数据局部性原则划分块，因此本文方法与 Finesse 的 DCR 均不理想。同时，Kernel tar 代码数据集中多数文件小于 16KB，多数文件可能被当作单块，无法按可变粒度划分，导致与 Finesse 的 DCR 差距逐渐缩小。

如图 3，当块大小为 **16K** 时，本文与 Finesse 差距为 **9.52%**。从 2KB 到 8KB，本文 DCR 分别比 Finesse **高 17.85%、16.95%、13.29%**。尽管随块长度增加，局部性优势逐渐减弱、与 Finesse 差距缩小，总体而言本文去重效率仍高于 Finesse。

**图 3**：Linux Kernel 工作负载上的 DCR

---

#### SQL Dump 工作负载 — DCR（图 4）

由于 dump 工作负载特性，SQL Dump 数据集存在大量冗余数据。平均块长度较小时，相同内容会产生更多增量文件，占用更多存储空间。因此，随块长度增加，Finesse 的 DCR 逐渐上升，而本文方法的 DCR 逐渐下降——块长度增大后冗余块概率降低，难以按可变粒度划分数据，多数数据以粗粒度方式处理，去重精度逐渐下降。

尽管本文 DCR 逐渐下降、Finesse 逐渐上升，**本文 DCR 仍高于 Finesse**。可变粒度处理能有效减少块数量、降低元数据开销并提高 DCR。

**图 4**：SQL Dump 工作负载上的 DCR

---

#### macOS 工作负载 — 总耗时（图 5）

如图 5，当块大小为 **2KB** 时，本文速度约为 Finesse 的 **11.07 倍**。主要因为 Finesse 需以块为单位对块内数据进行指纹计算，并进行分组、排序等操作以得到特征向量，在小块条件下耗时更高。而本文对块进行可变粒度处理，减少块数量与元数据开销，并聚焦计算最可能含冗余数据的块。

块长度从 **4KB 到 16KB** 时，Finesse 耗时分别为本文的 **4.43、3.42、2.29、1.15 倍**。可见随块长度增加，本文优势逐渐减小，但仍快于 Finesse。块长度增大时，每块内冗余比例逐渐降低；本文需对多数块做细粒度处理以保证去重精度，块数增加，耗时逐渐接近 Finesse。尽管如此，随块长度增加，两种方法的块数均减少，检测耗时逐渐降低；比较而言本文耗时仍更低。

**图 5**：macOS 工作负载总耗时（秒）

#### Linux Kernel 工作负载 — 总耗时（图 6）

如图 6，块大小从 **2KB 到 8KB** 时，本文耗时低于 Finesse，约为 Finesse 的 **1/5**。Finesse 需对所有数据做细粒度扫描，并通过分组、排序等方式获得特征向量做相似检测，耗时较高。然而，如前所述，块长度增大时冗余比例下降，多数数据需细粒度处理，本文速度逐渐与 Finesse 相当。如图 6，块长度达 **16KB** 时，两者耗时相近，甚至可能相同。

如图 7，块大小从 **2KB 到 16KB** 变化时，由于获得的块数减少，本文与 Finesse 的速度均提升，整个去重过程耗时降低。但该过程中 Finesse 仍慢于本文，分别为本文的 **4.31、2.86、1.94、1.33 倍**。可见块较小时，本文的可变粒度块有潜力降低耗时；随平均块大小增加，本文仍优于 Finesse。

## VI. 结论（CONCLUSIONS）

随着云存储普及，数据去重通过消除跨用户重复数据、节省网络带宽，已成为广泛使用的技术。本文总结了最新相似数据去重工作，并基于观察分析其局限：紧跟相似块的块很可能具有数据局部性，反之亦然；不加区分地细粒度处理这些块会增加元数据；现有相似去重方案忽视元数据规模对性能的影响。

因此，我们提出面向云存储的**快速可变粒度相似数据去重**：动态将相邻相似块或唯一块合并为较大块以降低元数据，同时保留位于相似块与唯一块**过渡区域**的块的拆分，以维持高去重比。最后实现原型并在真实数据集上实验，结果表明：本文方法在保持高去重比的同时，**显著降低元数据规模**。
