# 五条 trace 零误差重映射 + 匹配池重建 + 删除清单

记录时间：2026-08-10 14:05 (UTC+8)

## 1. 任务与结论

按三级策略对全部五条 trace 重新匹配，**474 万个唯一对象 100% 覆盖、每个对象
payload 与 trace size 逐字节相等（零误差）**；同时重建了池索引、统计文件使用

`scripts/cloud/remap_zero.py`。

## 2. 关键设计：配方式清单（manifest），不改盘上文件

零误差不再靠物理改写文件（474 万对象不可行），而是每条 trace 生成一份确定性
映射清单 `/data/manifests/<trace>.manifest.csv.gz`：

    obj_key, size_trace, file_rel, file_size, offset, delta, action

回放时按配方生成 payload（读文件/区段、修剪或微量补齐到恰好 S 字节）。
盘上文件保持原样。这继承了 SkyStore 作者"按规则现场生成 payload"的思想。

## 3. 最终三级算法（对象从大到小处理）

- **L1 整文件**（action=exact/trim/pad）：±10MB 窗口内最近的未用文件。
  - exact：文件大小恰等于 S；
  - trim：文件略大，payload 取文件前 S 字节（纯真实连续字节）；
  - pad：仅当缺口既 ≤64KB 又 ≤对象的 5% 时允许微量同族补齐。
- **L2 区段划分**（action=extent）：整文件配不上的对象，从未被整文件占用的
  最大文件上切一段连续真实字节 [offset, offset+S)。同一 trace 内区段互不
  重叠 → 对象间内容零共享，不虚增去重率。供给从"文件个数"变为"字节总量"
  （1.4TB），彻底消除短缺。
- **L3 空对象**（action=empty）：S=0 的对象 payload 为空。

指派完全确定性（输入排序 + 贪心），无随机种子，可复现。

## 4. 迭代过程（三版算法）

1. **最近邻**：T015 暴露供给短缺——池中 ≥100KB 的文件仅约 28 万个，
   T015 需要 67 万个，pad 占比 74.8%（自我循环补齐污染去重实验）。
2. **trim-first**：pad 降不下来（65%），且出现从 42GB 文件修剪小对象的
   畸形指派。结论：供给问题算法治不了。
3. **extent 区段划分**（最终版）：pad 占比全部 ≤1.2%。

另发现：旧 `pool_sizes.npy` 含 8 月 9 日已删除的文件，此前 T079 "100%"
虚高；本次重扫索引（18,133,894 个文件）后为真实数字。
