## 执行摘要

三轮审查发现了 **6 个阻塞级 bug**。4 个方法为零调用点死代码，1 个硬编码策略名白名单遗漏导致对象永远 stuck 在 `pending` 状态，1 个网络成本完全无追踪。本轮已全部修复。

**核心结论：修复前 DedupAwareTevict 等效于 `always_store`（base region TTL=-1）+ `always_evict`（非 base region TTL=0），网络成本=0，`stats()` 永不输出，Phase 2 去重公式死代码。**

```304:305:policy_dedup_aware_tevict.py

        return [req.client_from_region]
```

对象只写入 client 自身 region。与 SkyStore 完全一致。

### 1.2 `start_upload` → `get_ttl()` → base region TTL=-1


因为 `fixed_base_region=True` → `get_ttl()` 立即返回 -1（永不过期）。与 SkyStore 相同。

### 1.3 ~~BUG 1 [已修复]~~ `complete_upload` 策略名白名单遗漏

**原代码**（put.py:408-420）:


## 二、GET 链路：DEDUP 对象如何获取？

### 2.1 `locate_object` → TTL 决策

在 GET handler 中（get.py:138-179），当对象已在某 region 存在且 client 不在 base_region，会调用 `get_ttl(src, dst, fixed_base_region=False)` 计算 TTL：

#### Phase 1: `_compute_skystore_ttl` — SkyStore 自适应 TTL

与 `policy_skystore.py` 逻辑完全一致（histogram → `calc_evict_cost` → `find_min`），返回 `region_pairs_ttl[(src, dst)][-1]` 作为 `adaptive_ttl`。

实验初期（无历史数据）：
- `calc_evict_cost` 中 `next_hist` / `next_last_hist` 均为空 → 返回 `(-1, -1)`
- `find_min` 中 `noPastData=True` → `ttl = teven / 7200 * 3600 = teven/2` 秒

#### Phase 2: Dedup-Aware 存储形式决策

```572:596:policy_dedup_aware_tevict.py
        teven_sec = self._compute_teven(src, dst)
        L = self.get_chunk_L(dst) if dst else 0.0
        tau_effective = (1.0 - L) * teven_sec

        with self._dedup_lock:
            ttn = self._dedup_time_to_next
            key = self._dedup_key

            if ttn is None or ttn <= 0 or key is None:
                return 0

            if ttn <= tau_effective:
                self._obj_state[key] = ObjState.HOT
                self._transitions_to_hot += 1
                return adaptive_ttl
            else:
                self._obj_state[key] = ObjState.DEDUP
                self._transitions_to_dedup += 1
                return 0
```

### 2.2 ~~BUG 2 [已修复]~~ `set_key_context()` 从未调用 → Phase 2 死代码

**问题**: `_dedup_time_to_next` 和 `_dedup_key` 仅由 `set_key_context()` 设置，但该方法**零调用点**。

**后果**: `ttn` 永远为 `None` → Phase 2 永远命中最前面的 `return 0` → `get_ttl()` 对非 base region 永远返回 0。

**修复**:
1. `object_schemas.py`: 在 `LocateObjectRequest` 添加 `time_to_next_access: Optional[float] = None`
2. `get.py`: 在 `get_ttl()` 调用前插入 `put_policy.set_key_context(request.key, request.time_to_next_access)`

**剩余工作**: `run_client.py` 需要在 trace 重放时将 `.aug` 格式的 `time_to_next_access` 列传递给 `LocateObjectRequest`。

### 2.3 ~~BUG 3 [仍缺失]~~ `set_obj_chunk_refs()` 从未调用

`_obj_chunk_refs` 和 `_obj_manifest_size` 永远为空。

**影响**: GET 的 `chunk_manifest` 永远返回 `None`，CLEAN 的 manifest 大小永远回退到 1024。

**修复时机**: 需要在 PUT handler 中集成 `DedupEngine.chunk_and_dedup()`，并在成功后调用 `put_policy.set_obj_chunk_refs(key, manifest)`。

### 2.4 ~~BUG 4 [仍缺失]~~ `record_chunk_locality()` 从未调用

`_chunk_local_hits` 和 `_chunk_total_checks` 永远为空 → `get_chunk_L()` 永远返回 0.0 → `tau_effective = 1.0 * teven_sec`（无去重折扣）。

**修复时机**: 需要在 PUT handler 中 commit 前，用 `DedupEngine` 计算 chunk local/remote hits，调用 `put_policy.record_chunk_locality(region, local_hits, total)`。

## 四、存储成本：DEDUP 差异分析

### 4.1 `add_to_cost()` 公式验证

```292:302:policy_dedup_aware_tevict.py
    def add_to_cost(self, timedelta: int, region: str, size):
        added_cost = (
            timedelta / 3600 / 24
            * self.stat_graph.nodes[region]["priceStorage"]
            * 3
            * size / (1024 * 1024 * 1024)
        )
```

**公式**: `cost = seconds/86400 × priceStorage × 3 × bytes/GB` ✓ 单位正确

### 4.2 HOT vs DEDUP 成本对比

| 对象类型 | 大小 | TTL | 日数 | 单价 | 存储成本 |
|---------|------|-----|------|------|---------|
| HOT (100MB) | 100 MB | 7h | 0.29天 | $0.026×3 | **$0.0022** |
| DEDUP (1KB manifest) | 1 KB | 1 min | 0.0208天 | $0.026×3 | **$1.6×10⁻⁹** |

DEDUP 存储成本 ~140 万倍于 HOT（因为 TTL=0 经 `round_to_next_30_min` 最多留 30min + manifest 才 KB 级）。

### 4.3 验证清单 ✓

- [x] `clean_object` 中 DEDUP 对象使用 `get_obj_manifest_size()` (clean.py:91-99)
- [x] `clean_out_remaining` 中 `dedup_aware_tevict` 已在策略名列表中 (clean.py:291-294)
- [x] `network_cost` 输出在 `clean_out_remaining` 中 (clean.py:300)
- [ ] PUT overwrite 路径 (put.py:135) 仍然使用完整 `logical_object.size` — 但这是微小的，因为 PUT overwrite 只发生在 hot→hot transition

## 七、总结

| 严重度 | 数量 | 状态 |
|--------|------|------|
| **审查前严重** | 6 | ✅ 全部已修复 |
| **剩余未修复** | 5 (M1-M5) | ⚠️ 需远程接线 |
| **低优先级** | 1 (L 永远为 0 导致无去重折扣) | ⚠️ 依赖 M3+M4 |

**修复后的链路可运行状态**: DedupAwareTevict 现在可以正确运行 PUT→complete_upload→ready→GET→Cost 主线。Phase 2 决策逻辑可达（`set_key_context` 已接线），网络成本有追踪（`add_to_network_cost` 已接线），`stats()` 可输出。但 `DedupEngine` 仍未接入（M3），chunk locality 仍为 0（M4）。

**对消融实验的影响**: 在 DedupEngine 完全接入前，实验数值不能反映真实去重效果。当前可用于验证框架逻辑（单变量：存储形式决策是否正确传递到下游），但缺少 chunk 级别的 dedup ratio、L 值、网络传输量等核心消融指标。
