# 跨区去重索引设计：数学建模 + 文献最佳实践

记录时间：2026-08-10 14:50 (UTC+8)

## 0. 问题

传统去重两个关键指标：**去重率**（省多少字节）与**索引检索时长**（每个 chunk
的指纹查找延迟）。跨区场景下索引放哪里，直接决定 PUT/GET 的延迟路径与
存储费/运费结构。目标：消除冗余、降低总成本。

## 1. 符号

| 符号 | 含义 | 典型值 |
|---|---|---|
| S | 对象大小 | trace 给定 |
| c | 平均 chunk 大小（FastCDC） | 8 KB |
| N_c = S/c | 对象 chunk 数 | 1GB → 131,072 |
| n | 单区唯一 chunk 数 | 1.1TB 池 ≈ 1.4×10⁸ |
| p_s | 存储单价 | ~0.023 $/GB·月 |
| p_x | 跨区传输单价 | ~0.09 $/GB（双向计费更高） |
| δ_loc(r) | 新对象字节在区 r 已存在的比例（本地去重率） | 数据集属性 |
| δ_dst(r) | GET 目的区已有该对象 chunk 字节比例 | 同上 |
| RTT_x | 跨区往返延迟 | 50–300 ms |
| t_idx | 单次本地指纹查找 | 见 §3 |
| φ | 碎片化读放大因子 | 1–3 |

## 2. 四种跨区索引架构及其 PUT/GET 影响

### A. 全局集中索引（控制面单点）
- PUT：每对象至少 1 次跨区批量查询 → T_put += RTT_x；索引单点 QPS 瓶颈。
- 若跨区只存引用（不物化）：GET 要去别的区拉 chunk，**每次 GET 都付运费**，
  p_x ≫ p_s 时必亏（0.09 $/GB 运一次 ≈ 存 3.9 个月）。
- 结论：只能做元数据目录，不能做数据面去重依据。

### B. 纯本地索引（各区独立去重）
- PUT/GET 零跨区 RTT；但去重只在区内生效，跨区传输每次都是全量 S。
- 丢掉的是"目的区已有 chunk 不必重传"这块最大的运费节省。

### C. 指纹空间哈希分片（fp → home region）
- PUT：N_c 个查找散射到 |R| 个区（按区批量）→ T_put += max RTT_x；
- 更致命：chunk 归属与数据局部性解耦 → GET 需从多区拼装对象，运费爆炸；
- 学界结论：指纹查找的性能全靠**流局部性**（DDFS 的 SISL+LPC、Sparse
  Indexing 的分段采样），哈希分片恰好摧毁局部性 → 缓存命中率崩塌。
- 结论：不可取。

### D. 本地全量索引 + 控制面全局 chunk 目录（异步）【采用】
- 每区：Bloom（内存）+ LMDB（fp → region/offset/size，NVMe）全量本地索引；
- 控制面：obj_key → manifest（fp 列表）+ 每区 chunk 存在位图，**异步**更新，
  不在 PUT 关键路径；
- PUT：只查本地（μs 级），零跨区 RTT；
- 跨区 GET：控制面本来就在 GET 路径上（SkyStore locator），顺带算
  chunk 差集 → 源区只发目的区缺失的 chunk，运费 (1-δ_dst)·S·p_x。

## 3. 索引本身的规模与检索时长（架构 D 的工程数值）

- **Bloom**：m = 1.44·n·log₂(1/ε) bit。n=1.4×10⁸、ε=1% → ≈ 240 MB 内存/区。
  查找 ~0.1 μs。对"新 chunk"绝大多数在 Bloom 层直接判掉（DDFS 报告
  可消除 99% 磁盘查找）。
- **LMDB**：条目 ~64 B（fp32 + 位置），1.4×10⁸ 条 ≈ 9 GB NVMe，B+树查找
  热页缓存后 ~5–20 μs。
- **PUT 时延分解**（单线程，1 GB 对象）：
  T_put = S/B_cdc + S/B_hash + N_c·t_idx + (1-δ_loc)·S/B_store
  ≈ 0.5 s(FastCDC ~2GB/s) + 0.3 s(BLAKE3 ~3GB/s) + 131072×(0.1μs+h·10μs)
  ≈ 0.8 s + h·1.3 s（h=命中率）。8 核并行后与网络上传时间重叠，
  **索引不是瓶颈**；跨区方案（A/C）一个 RTT 就抵消全部本地开销。
- 内存不够时的降级路径（文献）：Sparse Indexing 采样 1/64 进内存；
  CPI（IEEE TC'24）部分索引在同等内存/IO 约束下比全量索引吞吐高 37–122 倍，
  去重率只降 4%。

## 4. 成本建模（PUT/GET 全路径）

### 4.1 PUT（首次写入区 r）
- 存储增量：(1-δ_loc(r))·S·p_s/月 + 索引开销 ≈ 0.8%·物理字节
  （64B/8KB）；
- 运费：0（本地去重，不跨区）；
- 请求费：manifest 写 + chunk 批量写（按 4MB 聚合上传，请求费可忽略）。

### 4.2 GET（区 r' 请求，对象在 r）
三种状态（DedupAwareTevict）：
1. **HOT 命中**（r' 有物化副本，TTL 内）：零运费，读放大 φ=1；
2. **DEDUP 命中**（r' 只有引用+chunk）：零运费，读放大 φ∈[1,3]
   （碎片化；TiDedup 的对策是热 chunk 提升/物化 = 我们的 HOT 态）；
3. **未命中**：传输 (1-δ_dst(r'))·S，费用 p_x·(1-δ_dst)·S；到达后
   物化（HOT）或只存缺失 chunk + 引用（DEDUP）。

**第二次 GET 的影响**（用户此前的问题，量化）：
- 若保持 HOT：零运费，代价是重复副本存储 S·p_s；
- 若退化 DEDUP（物理副本删，chunk 留）：零运费 + φ 读放大，
  存储只付 (1-δ)·S；
- 若 chunk 也被逐出：重付 (1-δ_dst)·S·p_x。

### 4.3 chunk 级驱逐的盈亏平衡（把 Tevict 推广到 chunk）
保留 chunk x（大小 c）到下次访问的期望时长 τ 满足以下则保留：
  c·p_s·τ ≤ c·p_x·P(τ 内被再访问)
临界点 τ* = p_x/p_s ≈ 0.09/0.023 ≈ **3.9 个月**。
去重带来的两个修正（这就是 DedupAwareTevict 的核心）：
1. **共享聚合**：chunk 被 k 个对象引用 → 再访问率是 k 个对象访问率之和
   λ_x = Σ_o λ_o·1[x∈o] → 高引用 chunk 应显著延长保留（InftyDedup 用
   引用数修正预期读频率，平均再降 11% 成本）；
2. **部分重传**：逐出后重传只付缺失部分，期望惩罚从 S·p_x 降为
   (1-δ_dst)·S·p_x → 驱逐更激进也安全。

### 4.4 总成本目标函数
  C = Σ_r p_s·∫[(1-δ_r)V_r(t) + V_hot(t) + 0.008·V_r(t)]dt
      + Σ_{跨区GET} p_x·(1-δ_dst)·S + 请求费 + 计算费(CDC+hash)
对比 SkyStore 基线（C₀ = 副本存储 + 全量 S 传输）：
- 存储节省因子 ≈ δ（冷数据引用化）；
- 运费节省因子 ≈ δ_dst（差量传输）；
- 新增成本：索引 0.8% 存储 + 每 GB 约 0.5–1 s 单核 CPU + 控制面元数据。
δ 越高、跨区重复访问越多，净收益越大；δ→0 时退化为基线 + ~1% 开销。

## 5. 文献最佳实践对照

| 系统/论文 | 关键做法 | 对我们的启示 |
|---|---|---|
| DDFS (FAST'08) | Bloom + 流式布局 + 局部性缓存，消除 99% 磁盘查找 | 本地索引配置的黄金标准 |
| Sparse Indexing (FAST'09) | 采样 1/64 + 分段相似性 | 内存不足时的降级路径 |
| CPI (IEEE TC'24) | 部分索引 SOTA：recipe-segment + container-catalog | 同上，最新参照系 |
| TiDedup (ATC'23, Ceph 主线) | CDC + 选择性去重 + OID 反向指针引用；热 chunk 提升回 base tier | 引用管理方案；HOT/DEDUP 二态被生产系统验证 |
| InftyDedup (FAST'23) | 去重全在云内批处理（PB 级几美元）；按 chunk 引用数/访问预测选 hot/cold 存储，省 26–44% | 异步/批式去重 + chunk 级成本分层 = 我们 §4.3 的直接印证 |
| PM-Dedup (arXiv'25) / POFFO (NAS'24) | 云→边下发高频指纹子集（share-index），本地先查 | 可选优化：向对端区推送 top-k 热指纹做预过滤 |
| Data Domain Cloud Tier (ATC'19) | 先本地去重、再上远端层 | "去重发生在数据所在地"原则 |
| 工业实践（AWS 成本优化） | 跨区传输前 dedup+压缩；Skyplane 覆盖网络 | 差量传输 + 压缩叠加 |

共同结论：**指纹索引永远放在数据所在地（区内全量），跨区只走异步元数据
和差量数据；没有任何生产系统把同步全局指纹查找放在写路径上。**

## 6. 设计定案（DedupAwareTevict 索引层）

1. 每区 Bloom(240MB, ε=1%) + LMDB(~9GB NVMe) 全量本地索引；PUT 零跨区 RTT。
2. 控制面存 obj→manifest 与区级 chunk 位图（~6GB 量级），异步更新；
   跨区 GET 由控制面算差集，只传缺失 chunk（批量 4MB + 压缩）。
3. chunk 级 TTL：τ*(x) = (p_x/p_s)·(1-δ_dst)⁻¹ 修正，引用数 k 加权延长；
   热 chunk 物化为 HOT 副本（消除 φ 读放大），冷 chunk 保留引用。
4. 索引开销计入成本模型（0.8% 存储 + CPU），实验中如实报告。
